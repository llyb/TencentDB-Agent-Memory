# 任务一：Proxy 工具注入 P0/P3 实验报告

## 1. 实验结论

在本地已配置的 `glm-5.2` OpenAI-compatible 服务上，对固定 test split 运行 P0/P3 各 3 个 seed，共 600 次行为请求；另运行 100 次无注入请求，仅用于扣除共同 Token 开销。

| 版本 | 有效调用率 | 误调用率 | 工具选择正确率 | Provider 实测注入 Token/请求 |
|---|---:|---:|---:|---:|
| P0 (`50f33f5`) | 100.00% (180/180) | 17.50% (21/120) | 91.67% (165/180) | 4246 |
| P3（当前实现） | 98.33% (177/180) | 0.00% (0/120) | 100.00% (177/177) | 1694 |
| 变化 | -1.67 pp | -17.50 pp | +8.33 pp | -2552（-60.10%） |

按方案中的门槛，P3 可以保留：Token 降幅超过 30%；有效调用率下降 1.67 个百分点，没有超过允许的 3 个百分点；误调用率和工具选择正确率均改善。

## 2. 实验设置

- 日期：2026-09-04。
- 模型：`glm-5.2`。
- 协议：OpenAI-compatible chat completions。
- 解码参数：`temperature=0`、`max_tokens=512`、seed 为 1/2/3。
- 数据：`proxy-test.jsonl`，每个 seed 包含 Memory 20、Skill 20、Knowledge 20、None 40。
- 工具环境：向模型提供一个原生 `Bash` function tool。只有 Bash 命令命中 memory bridge、skill bridge 或 knowledge `/tools/list|call` 时才记作资产工具调用；普通 Bash 调用不算误调用。
- 停止点：只分析模型首个响应中的首次资产工具调用，不执行 curl，不评价工具返回资产质量。
- P0：运行时从 Git 基线 `50f33f5` 提取原始 renderer。
- P3：运行当前公共决策策略、精简工具契约和正负触发边界。

三个 seed 即使在 `temperature=0` 下也得到不同结果，说明当前上游未提供完全确定性的采样；因此报告 pooled 原始计数，而不是选择表现最好的一次运行。

## 4. Token 口径

为了得到模型服务实际 tokenizer 下的注入量，对同一批 100 条 query 运行一次无注入对照。其 provider prompt usage 平均为 230.22 Token/请求，包含共同 system、query 和 Bash tool schema。

- P0 provider prompt usage 平均 4476.22，扣除共同开销后为 4246 个注入 Token。
- P3 provider prompt usage 平均 1924.22，扣除共同开销后为 1694 个注入 Token。
- 实测减少 2552 Token/请求，降幅 60.10%。

另外使用 `o200k_base` 做离线复现，固定夹具得到 P0 4468、P3 1716，减少 2752（61.59%）。该静态值只用于无模型环境下快速回归，最终结论采用上面的 provider usage。

## 5. 错误分析

### 5.1 P0 的主要问题

P0 共出现 36 次错误：15 次正例工具家族选错，21 次 None 误调用。

1. Skill 请求先查 Memory。旧提示在多处重复强调“历史、约定、规则必须先查记忆”，模型面对“团队已有流程，不要自行发明步骤”时经常先调用 Memory，再准备调用 Skill。由于主指标看首次家族，这些样本被判错。
2. 普通 coding 被 Knowledge code-graph 吸引。P0 把“了解项目、找入口、定位符号、影响面”等场景描述得过宽，导致“为现有 API 写示例”“优化当前 SQL 索引”“为本地命令增加参数”等明确要求使用当前输入/本地代码的请求仍调用 Knowledge。
3. 普通 coding 被 Memory 强制规则吸引。部分模型把“当前函数、项目约定、参数”等词扩展解释成可能存在历史信息，调用了 atomic/search。

### 5.2 P3 的剩余问题

P3 没有误调用，也没有调用后选错家族，但发生 3 次漏调用：

- `test-skill-011`, seed 2：模型说要搜索基准测试 skill，却没有真正发出 Bash 调用。
- `test-skill-015`, seed 3：模型说要检查团队 Skill/Wiki，但没有发出 Bash 调用。
- `test-knowledge-014`, seed 3：模型正确识别 code-graph 与 wiki，输出在生成工具调用前被截成说明文本。

这三例表明 P3 的剩余风险是模型“口头计划调用但未调用”，不是路由混淆。后续若继续优化，应在公共规则中小幅强化“需要资产时首个动作直接调用”，不能恢复 P0 的大范围强制触发，否则可能重新引入误调用。

## 6. 结果边界

- 数据集是为本项目自建的决策集，能够测注入路由，但不能代表所有真实 coding 分布。
- test 中同类请求采用模板化构造，当前结果可能高于真实线上复杂请求。
- 本实验只有 `glm-5.2`；跨模型通用性仍需另行验证。
- 没有执行工具或评价最终回答，因此不能把结果表述成 coding 任务成功率提升。
- P1/P2 没有单独运行；本轮只回答 P0 到最终 P3 的总体收益，无法把收益进一步归因到机械去重、最小描述和正负边界中的某一个单独步骤。
