## 1. 这次测试回答什么

旧实验把整段原始会话放入临时检索表，只能评价会话文档检索。本次实际调用生产模块执行：

```text
论文官方历史 → L0 原文录入 → L1 模型抽取/冲突处理/去重
  → L2 场景工具写入 → L3 画像工具写入 → 冻结快照
  → L0/L1 真实 SQLite BM25 / BGE-M3 / RRF
  → L3 注入、L2 导航与按需读正文 → GLM 回答 → 官方 rubric 双裁判
```

它是完整**记忆数据链路**的离线测试：覆盖保存、组织、检索和回答。执行器显式推进各阶段，不测试部署进程的异步调度、队列竞争、Proxy 注入模板、Claude Code UI、ACL、跨租户隔离或负载性能，也不包括方向三的 Skill 效果。不能表述成“整个项目所有功能均已通过”。

L0/L1 首次查询固定由执行器发起，以隔离检索算法变量；后续 `read_scene` 由回答模型自主调用。这里不评价模型是否正确决定调用 L0/L1 工具，那个问题属于方向二。

## 3. 评分与指标口径

- QA 使用作者 [evaluate_qa.py 原版五类提示词](https://github.com/xiaowu0162/LongMemEval/blob/9e0b455f4ef0e2ab8f2e582289761153549043fc/src/evaluation/evaluate_qa.py)，主裁判 `glm-5.2`，所有答案由 `qwen3-235b-a22b-instruct-2507` 独立复核；严格解析 yes/no。模型选择与论文不同，结果不是官方排行榜可比成绩。同模型主裁判有自评偏差，双裁判一致也不等于人工真值。
- QA 分母包含全部七题；拒答只从检索指标分母排除。某条件有未完成题时完整准确率为 null，不能以 completed-only 准确率代替。
- Recall 判断检索记录是否来自官方证据会话，分别统计 L0、L1 及二者并集。联合最多十条记录，不是十个不同会话，也不是旧基线的五个会话；不能与旧 Recall@5 相减为提升。
- L1 来源 ID 有效性、来源会话覆盖只检查追溯关系，不等于摘要完整保留答案或不存在幻觉。回答结果、上下文和具体失败案例共同用于归因。
- 以题为单位做配对差值和 2,000 次 bootstrap。七题区间仅作描述，没有足够证据支持“显著提升”或跨数据集泛化。
- 若七题全部正确，经验 bootstrap 会退化为 `[1,1]`；这只是当前七条观测没有差异，不是总体准确率的保证。同理，配对差值全为 0 的区间不能证明两种方法等效。
- 耗时区分原始记忆构建、向量索引及回答；回答耗时含初次检索和场景读取、不含裁判。固定顺序和向量缓存会影响时延，不将一次小样本均值当作生产 P95。
- Token 仅累计服务端返回的 usage，失败未返回 usage 的实际消耗未知；未提供单价，不估算人民币或美元金额。向量索引是共享实验准备成本，不应给无记忆/BM25 条件重复计费。

## 4. 实现、调试与保留的限制

新增系统编排、生产记忆适配器、模型日志、冻结快照复用，以及官方 rubric 判分；复用原有数据加载、SQLite 搜索、哈希和 bootstrap。旧 BM25 会话基线仍有独立诊断作用，因此保留；没有保留第二套自建 benchmark。

实际接入修正了生产 L0 BM25 结果缺少 session/user/agent 字段的问题，保证检索来源可追溯；同时修正 Standalone runner 与当前 AI SDK 的兼容参数、异步 storage 回调类型、可选备份/遥测模块初始化及 OpenTelemetry Resource API。

本轮保留了两类调试记录：

1. GLM 默认思考导致短探测输出预算耗尽，并增加抽取时延。评测请求统一关闭思考；短通路探测也做相应修正。
2. 初版 reader 先拼长画像再拼场景目录，可能让目录完全不可见；直接截断检索 JSON 也可能让长 L0 原文挤掉 L1。修正为先保证所有 L2 文件名可见，并按层交错打包检索记录、只裁剪正文；保留原始生成快照，全部问答与评分重新执行，旧回答不并入最终成绩。该修正是评测 reader 的修复，不声称线上 Proxy 存在或已修复同样的问题。

还实际观察到一次 HTTP 429 和一次 L2 整批 180 秒超时。429 由 SDK 重试恢复；超时题 `a82c026e` 首次明确失败，场景目录由生产模块回滚，保存首次 `attempt-1-summary.json` 后，以原源码、原配置、原指纹恢复成功。没有重新选择题目，失败调用和已返回的 usage 仍留在账本内。这验证了本次本地文件模式下的一条恢复路径，不代表所有故障场景都已覆盖，也不代表首轮成功率为 100%。

恢复时 `build_ms` 只计该次函数执行耗时，读取已有会话检查点不会重计先前时间；索引耗时也会因缓存重用而变短。因此不把这些值加总成从零构建墙钟时间。跨尝试成本以完整 API 日志为准，最终回答对照首轮重新计算索引，恢复阶段可复用向量缓存；冷索引时间需查看首轮记录而非恢复后的耗时。

快照复用验证原始构建源码、模型、数据和内容哈希，原构建成本单列；最终运行重新生成 Embedding、回答和裁判标签。原始构建源码也已存入本地调试 run 的 `source/`，不覆盖它的旧指纹。自动恢复仅适用于完全相同源码和配置；改变读取策略应创建新 run。

当前仍未实施细粒度答案事实保留标注、模型自主 L0/L1 工具选择评测、多随机种子、全 500 题系统问答、时间重排、TCVDB 后端对照和线上负载测试。后续应依据错误归因选择下一项改动，而不是只增加召回数量。

另一个明确的生产语义边界是时间字段：[l1-writer.ts](../MemoryCore/src/core/record/l1-writer.ts) 的新增记忆将 `timestamps`、`createdAt` 设为实际写入时间；执行器沿用该字段提供给 L2，而 L0 保留作者历史日期。因此本次 2026 年运行时间不能解释为事件发生于 2026 年。实验没有事后替换这批时间字段来美化成绩。后续若优化时间题，应先区分事件时间、源消息时间和写入时间，并验证相对日期解析，再考虑基于时间的重排。
